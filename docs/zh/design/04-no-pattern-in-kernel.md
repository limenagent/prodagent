# 设计说明 04：为什么内核里没有 ReAct

## 一种很常见、但会越长越肿的做法

不少框架把 ReAct（“想一步、做一步、再想”的循环）直接写进最核心的 Agent 类：核心类里内置一个
while 循环，负责调模型、解析工具调用、再调模型。一开始很好用，可一旦你想支持“先规划后执行”、
固定流水线、或者某种自定义协作，就只能往核心类里加模式开关、加特殊分支。**每多一种编排，内核
就胖一圈**，而且这些模式彼此纠缠，谁也拆不下来。

## 我们的选择：内核只给原语，模式是拼出来的

这套内核反其道而行：它压根不知道“ReAct”是什么。它只给你几样中立的原语——节点（Node）、边
（Edge）、两种控制命令（`Goto` 回边/跳转、`Send` 动态扇出），以及“节点里可以放任何执行体”。

那 ReAct 去哪了？它被还原成了一张极小的图：一个“想”的节点调模型，一个“做”的节点调工具，再用
一条**回边**从“做”指回“想”，直到模型不再要工具就走向终点。也就是说，ReAct 不是内核里的一个类，
而是用内核原语拼出来的一种**配方（recipe）**，放在 `runtime/` 这一层：

```text
think（调模型）──要工具──▶ act（调工具）──回边 Goto──▶ think
   │                                          （于是形成 think⇄act 循环）
   └────────────不再要工具──────────────▶ final（收工）
```

同样地，“先规划后执行”是“一个规划节点 + 动态扇出若干执行节点 + 一个汇总节点”，固定流水线就是
几条写死的顺序边。**它们都不是新机制，只是同一把原语的不同摆法。**

## 这样做换来了什么

- **内核极其稳定**：再发明一百种协作模式，内核一行都不用改，改的只是上层配方。
- **模式无穷、且可绕过**：官方提供的配方不合手，你可以完全绕开它，直接用原语拼自己的，不会被
  框架的假设卡住。
- **认知负担反而更小**：你不需要记“这个框架支持哪几种模式、每种怎么配”，只需理解几样原语，剩下
  的是排列组合。

## 代价，以及我们怎么补

诚实地说，纯原语对新手不够友好——让每个人都自己拼 ReAct 也不现实。所以项目在原语之上提供了两层
“糖”：`runtime/` 里**官方维护**的常用配方（ReAct、plan-first、多 Agent），以及更顺手的门面 API
（`Agent`、`Workflow`）。九成场景开箱即用，剩下一成需要深度定制时，你随时可以下沉到原语。关键是：
**这些糖都在内核之外，可替换、可删除，而不是焊死在引擎里。**

## 对应代码

- `src/kernel/body.py`：唯一可组合接口，节点执行体可以是函数、工具、模型调用或子图。
- `src/kernel/command.py`：只有 `Goto / Send` 两种控制命令。
- `src/runtime/react.py`、`plan_first.py`：看 ReAct、plan-first 如何用原语拼出来。

> 怎么亲手用几行内核代码拼出一个 ReAct、再把它收成好用的门面，是配套专栏里非常有成就感的一段。
