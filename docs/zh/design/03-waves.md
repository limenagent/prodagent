# 设计说明 03：波次，为什么它是一致性边界

## 如果节点想跑就跑，会发生什么

设想三个节点并发执行，而且都能随时读写同一份共享状态。A 刚写了一半，B 就读到了这个“半成品”；
C 又基于 B 读到的半成品做了决策。你会得到一类最难排查的 bug：**结果取决于调度顺序，时好时坏，
无法稳定复现。** 模型本身已经够不确定了，框架不该在执行层再叠加一份不确定性。

## 一波一波地推进：先算齐，再一起提交

调度器因此采用“波次”（wave，本质是 BSP 整体同步并行）的节奏，每一波就三步：

```text
1) 算就绪：沿边算出“现在前置条件都满足”的节点集合
2) 并发跑：这一波节点同时执行，但谁都不直接碰共享状态，只各自产出 Outcome
3) 过屏障：等本波全部结束，统一折叠状态增量、应用控制命令、落一次检查点
```

关键在第 2 步：节点执行期间，共享状态对它来说是**只读快照**，它想改状态只能返回一份 `state_delta`。
真正的合并发生在第 3 步的屏障处，由 reducer 确定地折叠。这样一来：

- 同波节点互相看不到对方的半成品，**读到的永远是上一波结束时的一致状态**；
- 合并顺序无关，结果确定；
- 每一道屏障天然就是一个**提交点**：要么这一波完整生效，要么不生效，检查点正好落在这里。

动态扇出也落在这套节奏里：节点在第 2 步产出若干 `Send`，这些新实例进入**下一波**的就绪集合，
不会在本波中途插队，秩序因此保持得住。

## 诚实的代价：它不是免费的

波次模型不是只有好处。最明显的代价是**拖后腿节点（straggler）**：同一波里只要有一个节点跑了十
分钟，其余节点就算早做完，也得在屏障处等它，下一波才能开始。另外，波次把并发限制在“同一层就
绪节点”之间，不适合那种节点之间持续细粒度通信的场景。

这是一个清醒的取舍：对绝大多数 Agent 工作流，**“结果确定、好恢复、好调试”的价值，远大于极致的
并发吞吐**。真有节点耗时悬殊，可以把慢节点拆细、或用子 Run 隔离，而不是拆掉一致性边界。

## 对应代码

- `src/kernel/scheduler.py` 的 `drive()`：主循环就是上面那三步，短到几乎是这张图的直译。
- `src/kernel/graph.py` 的 `ready()`：纯函数地算每一波谁就绪。
- `src/kernel/channels.py` 的 `WaveWrites`：把本波增量先攒起来，屏障处一次性折叠。

> 屏障处“折叠状态、应用 Goto/Send、落检查点”这三件事为什么必须是这个顺序，配套专栏会逐行拆开。
