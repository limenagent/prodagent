# 设计说明 01：蓝图和一次执行，为什么必须分开

## 先看不分会怎样

很多人写第一个 Agent 框架时，会把“流程图”和“运行状态”塞进同一个对象：节点里既写着连接关系，
又记着“我这次跑到哪了”。看起来省事，很快就会撞上两堵墙。

第一堵墙：**没法复用**。同一张流程图，你大概率想同时跑很多个用户会话。如果状态长在图上，第二
个会话一开始就会看到第一个会话跑到一半的痕迹，你只能为每个会话复制整张图。

第二堵墙：**没法恢复**。“这张图长什么样”是不变的，“这次执行跑到哪了”是一直在变的。把两者
混在一起，你根本分不清存盘时哪些是该永久保存的图纸、哪些是这一次的临时进度。

## 分开之后，各归各位

于是我们拆成两个对象：

- **Plan（蓝图）**回答静态问题：有哪些节点、节点怎么连、状态有哪些通道。它是不可变的、可复用
  的、可以拿来做静态分析（比如检查有没有悬空的边）。同一张 Plan 可以同时被成百上千个 Run 复用。
- **Run（一次执行）**回答动态问题：这次跑到哪了、每个节点什么状态、当前共享数据是什么。它是一次
  性的、可序列化的，崩了就靠它的快照恢复。

一个很形象的比喻：Plan 是乐谱，Run 是某一场具体的演出。同一份乐谱可以演无数场，每场演出都有
自己的进度、自己的发挥，演砸了只影响这一场，不影响乐谱。

## 这个分离“白送”了哪些能力

一旦图纸和演出分开，几件原本很难的事突然就顺理成章了：

- **并发**：多个 Run 共享同一只读 Plan，彼此状态独立，天然不会串数据。
- **恢复**：只需要给 Run 拍快照，Plan 重新加载即可，职责清晰。
- **子流程复用**：一个节点的 body 可以是“再跑一张子蓝图”，因为蓝图本来就是独立、可嵌套的数据。
- **可视化和校验**：蓝图是纯数据，可以画成图、可以在运行前就发现“这条边指向了不存在的节点”。

## 一个容易忽略的细节

蓝图不可变，指的是**结构**不可变；但蓝图里节点的 `body`（真正干活的函数）是外部注入的执行体。
也就是说，图纸只描述“骨架”，不把某个模型厂商、某个工具实现焊死在里面。这为后面“端口注入、
离线测试”留好了位置。
