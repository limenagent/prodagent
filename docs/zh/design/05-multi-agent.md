# 设计说明 05：为什么多 Agent 不需要新引擎

## 常见做法：为“多 Agent”再做一套东西

很多框架一遇到多 Agent，就新增一批概念：主管 Agent、顺序 Agent、并行 Agent、循环 Agent、Swarm……
每种协作模式一个类，类越来越多，你还得记它们各自的用法。这其实是把“上层的协作策略”误当成了“内核
必须支持的新机制”。

## 回到本质：一个 Agent 调另一个，只是节点里又跑了一张图

回想前面的结论：节点的执行体（body）可以是任何东西——函数、工具、一次模型调用。那它当然也可以是
“**再激活一张子蓝图、递归地跑出一个子 Run**”。这就是多 Agent 的全部秘密：**不需要新引擎，子 Agent
就是某个节点的 body 递归调用了同一套内核。** 父 Run 和子 Run 在同一棵 Run 树上，事件写进同一条日志，
用的还是那个 Scheduler。

真正要讲清楚的，是两条**正交的轴**，把它们想明白，所有协作模式都迎刃而解。

**第一条是控制流轴：控制权怎么走。**

- **call（委派）**：父节点把子任务派给子 Run，**子干完把结果交回来，父继续**。控制权一定返回，结构
  上有保证，适合“主管派活、收齐再汇总”。
- **transfer（接力 / handoff）**：在同一张图里 `go` 到另一个 Agent 节点、且**不画回边**，于是控制
  权一去不返，由下家直接对用户负责。它不是新命令，就是一次普通 `Goto`，交接摘要走 payload。能不能
  交给谁，结构性地等于“图上登记了哪些 Agent 节点”。
- **黑板**：大家不直接互相调用，而是往一组共享状态通道里写，谁发现“轮到我了、数据齐了”谁就动，靠
  通道的 `when` 条件和汇聚规则驱动。

**第二条是状态轴：数据怎么共享。**

- **默认隔离**：子 Run 有自己的私有状态，父子之间显式声明“哪些下行注入、哪些上行回传”，没声明的不
  跨界。干净、可控。
- **共享黑板**：多个 Agent 显式共享同一组通道（比如共用消息历史），适合接力对话、专家共写一块板。

## 业界所有“模式”，都是这两轴的固定搭配

一旦用两轴看问题，那些唬人的名字就全部落位了，而且内核零新增：

| 业界叫法 | 控制流轴 | 状态轴 |
|---|---|---|
| pipeline 流水线 | 顺序静态边 | 隔离，上游输出映射给下游 |
| supervisor 主管-工人 | 父用 call 派活、收结果 | 隔离 |
| hierarchical 层级 | call 再嵌套 call，Run 树自然长出深度 | 层层隔离 |
| swarm 交棒网 | Agent 之间 transfer（同图 go、无回边） | 共享消息通道 |
| generator-critic 生成-批评 | call 出去、结果交回，可多轮 | 隔离 |
| blackboard 黑板 | 谁数据齐谁动 | 共享通道 + 条件触发 |

## 两个必须兜住的工程问题

递归组合很强，但有两个洞要结构性地堵上，而不是指望模型“自觉”：

1. **防环与限深**：A 派 B、B 又派回 A，Run 树会只增不减。嵌套委派用最大深度（`max_depth`）截断，
   同图平级转来转去用最大波次（`max_waves`）截断，超限直接判失败。
2. **失败沿树传播**：call 出去的子 Run 崩了，父不能把它当正常结果吞掉，失败要沿 Run 树向上穿透；
   而 transfer 之后控制权已经交出，取消权也随之转移。这两种语义必须分清楚。
