# 设计说明 02：状态为什么是事件“折叠”出来的

## 直觉做法：直接改一个字典

最自然的想法，是让每个节点跑完直接改共享状态：`state["cost"] += 1`、`state["messages"].append(...)`。
单机串行时没问题，但这套内核要支持**同一波多个节点并发执行**，于是两个麻烦同时出现。

一是**并发覆盖**：两个节点同时写同一个键，后写的把先写的冲掉，结果取决于谁跑得快，不确定。
二是**没有历史**：你手里只有“现在的最终状态”，不知道它是怎么一步步变成这样的——想审计、想回到
十分钟前、想崩溃后重建，都缺一份“过程记录”。

## 换个思路：只记发生过的事实，状态随时算出来

我们把这两件事一起解决，办法是**不直接存状态，而是只追加事件（Event）**。事件是“已经发生的、
不可变的事实”，比如“某节点完成了、产出了这些增量”。事件只追加、永不修改，形成一条事件日志
（EventLog）。而当前状态，是把这条事件流从头用**合并规则（reducer）折叠（fold）**出来的结果：

```text
初始状态 --事件1--> 状态1 --事件2--> 状态2 --事件3--> ... --> 当前状态
              fold            fold            fold
```

并发覆盖的问题，靠给每个状态通道声明 reducer 解决：消息通道用“追加”，成本通道用“相加”，当前阶段
通道用“后写覆盖”。引擎在波次屏障处统一折叠，结果与节点完成顺序无关，是确定的。没声明合并规则
的通道若被同波多个节点写，会直接报错，而不是悄悄丢数据。

## 这一个决定，同时买下三样东西

因为状态是事件流的投影，同一份事件日志顺手给了你：

- **审计**：状态怎么走到这一步，事件流就是完整轨迹；
- **崩溃恢复**：重放事件流即可重建状态，不需要别的机制；
- **时间旅行**：折叠到任意一个事件停下来，就是当时的状态。

它们不再是三个要分别开发的功能，而是“事件是唯一事实源”这一个决定的三个自然结果。

## 代价是什么，怎么补

诚实地说，纯靠重放有成本：一个跑了很久的 Run 可能攒下成千上万事件，每次恢复都从头折叠会慢。
办法是**快照 + 增量重放**：每隔一段把折叠结果存成快照（它只是个可丢弃的缓存），恢复时从最近快照
出发，只重放之后的事件。删掉所有快照，光靠事件日志依然能完整恢复——真相永远在事件里。
