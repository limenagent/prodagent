# 第 9 章 · 多 Agent 协作

> 本章讲三种协作机制——用最少的原语覆盖业界已知的全部协作模式。**最关键的一层：为了支持多 Agent，内核不需要新增任何调度机制**，三种协作全是已有原语的组合。

本章主线一句话：**能不拆就不拆；真要拆，原语要少到能全部装进脑子、又足够覆盖已知的每一种协作模式——三个机制，内核零新增。**

本章前置：第 4 章的 BudgetLedger（多 Agent 的账在这里汇合）、第 7 章的幂等思想、第 8 章的 Gate 一笔带过的权限检查。

---

## 9.1 第一个问题：什么时候该拆多 Agent

答案朴素得近乎扫兴：能不拆就不拆。

多 Agent 的成本清单不长，但每一条都实打实。更贵——多个 Agent 各自消耗 token。更慢——成员之间要通信、要互相等待。更难调试——出了问题，先要弄清是哪个 Agent 的错。还有一类单 Agent 没有的新病：互相推诿的死循环，A 说这事归 B，B 说这事归 A。

所以拆分要有过硬的理由，通常四选一：需要不同的专业能力（研究员、写手、审核员各司其职）；需要并行加速（同时查五个数据源）；需要互相制衡（多个意见投票或评审）；任务天然是流水线（A 的产出是 B 的原料）。**单 Agent 加上好的上下文管理（第 6 章）能搞定的事，就不要拆**。

还有一条反面教训：如果发现自己在纠结"选哪种协作模式听起来更酷"，多半已经走偏了。**让协调的复杂度超过任务本身的复杂度，是事倍功半的经典配方。** 正确顺序是：从最简单的能解决问题的模式开始，跑起来，观察瓶颈，再逐步演进。

## 9.2 三种机制，内核零新增

两个自主单元要协作，只问两个问题就能穷举出三种机制：**控制权回不回来**，和**数据怎么过去**。

| 维度 | call 委派 | transfer 交接 | 黑板 |
|---|---|---|---|
| 控制权 | 返回，父始终在控 | 不返回，当前方退场 | 没有控制权交接 |
| Run 结构 | 树深一层，之后弹回 | 同层接力，栈不增长 | 各 Run 独立 |
| 数据 | 参数传入、结构化结果传出 | 随交接带一份摘要 | 读写共享通道 |
| 触发 | 父主动调用 | 当前方决定交给谁 | 数据变化触发 |

**委派（call）**——把另一个 Agent 当成一个工具。父在自己的执行过程中，把一个边界清晰的子任务交给子 Agent；子用自己的 AgentSpec 跑完整的推理循环，产出一个结构化结果；父拿到结果继续。从内核看，这就是第 3 章的「一个节点的 body 激活一个子 Run」（`SubPlanBody`）——控制权**结构性地**保证返回，子再怎么内部折腾，都封在它自己的 Run 里，父只等一个干净结果。业界叫 agent-as-tool。

**交接（transfer）**——交出去不回来。当前角色判断"接下来该由另一个角色负责"，就把主导权交给对方，自己退场。内核上是 `Handoff` 控制词：当前分支不等待、直接终止，激活目标 Run 接续——**不是叠深一层等返回，而是同一层的一次接力，Run 栈不增长**。这里有个经典的"粘性"坑：如果"要不要交回"也交给模型用一次工具调用来决定，用户就可能被困在某个角色里出不来。对策三条：该返回的场景结构上就该用 call；交接配显式的可交接白名单；加跳数上限兜底，绝不让用户悬在半空。

**黑板**——谁都不调用谁，靠共享状态联动。一个角色把中间产物写进某条状态通道，另一个角色的触发条件由这条通道决定，条件满足就醒来读数据接着做。它用的全是学过的东西：条件边 `when`（第 3 章）负责"什么时候该醒"，状态通道和 reducer（第 7 章）负责"多方写不丢数"。黑板本质是**共享作用域里的若干通道**，耦合最松、便于多方并行，代价是执行顺序不显式、共享状态要治理。

**点题：三种机制，内核零新增。** call 是父子 Run（10 课），transfer 是运行时选边在协作场景的特化（06 课），黑板是通道加条件触发（05/07 课）。三种机制真正的区别，只落在两个地方：汇合语义（等返回 / 接力不返回 / 不汇合），和状态作用域（私有加映射 / 共享）。内核要提供的只是父子 Run、一个显式的汇合字段，再加通道作用域——三机制就全齐了。

## 9.3 激活的抽象：协作机制不感知位置

所有"让一个 Agent 干活"的动作——委派一个子 Agent、交接给同侪——在代码里都是同一个调用，一次**激活**（`RunnerPort.activate()`）。激活的入参只带可序列化的字段：哪个 Agent、什么任务、哪个运行、挂哪个账本。至于这个 Agent 在本进程执行还是在另一台机器上执行，由端口的实现决定，协作机制完全不感知。

这是端口思想在多 Agent 层的最后一次应用：协作的语义（谁跟谁、什么顺序、共享什么）和执行的物理（哪里跑、怎么通信）被彻底分开。想从单机搬上集群，换一个端口实现，机制一行不改。

激活还配套一条"资源继承"：一个 Agent 派生子 Agent 或交接给同侪时，孩子继承父亲的一部分资源——预算上限、共享账本、检查点存储、事件日志、当前深度。接力的实现不是函数递归调用——当前这一步结束，驱动器拿着下一步的描述再启动一步。

## 9.4 治理：防甩锅、防越权、防打转

组织建起来后，三类故障会找上门：互相甩锅的死循环、越权操作、跑飞了停不下来。

防越权的机制是 Gate 检查器。框架不内建角色权限系统，而是在总线的 VETO 通道上提供通用拦截：你写一个检查函数，注册到某个拦截点，返回"拦截"就挡下。

```python
from prodagent.kernel.bus import Gate, BlockingResult
async def my_auth_checker(call, tool, run):
    if tool.meta.domain == "finance" and run.agent_name != "accountant":
        return BlockingResult(
            blocked=True,
            reason=f"Agent '{run.agent_name}' 不允许调用财务工具 {call.name}",
        )
    return BlockingResult(blocked=False)
hooks.register_checker(Gate.TOOL_CALL, my_auth_checker)
```

全框架一共九个拦截点，覆盖运行的关键节点：

| Gate | 拦截时机 |
|------|---------|
| `TOOL_CALL` | 工具执行前 |
| `PLAN_APPROVAL` | 计划审批 |
| `SESSION_START` | 会话启动 |
| `CONTEXT_BUILD` | 上下文组装 |
| `TOOL_RESULT` | 工具结果返回后 |
| `RUN_COMPLETE` | Run 完成前 |
| `APPROVAL_REQUEST` | 审批请求 |
| `AGENT_HANDOFF` | Agent 间交接 |
| `DOCUMENT_ADD` | 文档写入记忆前 |

被拦截的调用返回结构化的"被拦截"结果——模型看到拦截原因后可以自己调整。检查器本身抛异常时默认按拦截处理（fail-closed）——安全检查宁可错杀。

防打转的机制是**多层兜底**：

| 层级 | 机制 | 出处 |
|------|------|------|
| ① 预算硬上限 | 钱花完了必须停 | 第 4 章 |
| ② 波次上限 | 图执行有波数护栏 | 第 3 章 |
| ③ 无进展检测 | 共享状态指纹没变，主动终止 | 第 3 章 |
| ④ 交接跳数上限 | 接力链太长就停 | 本章 9.2 |
| ⑤ 进度守卫 | 重复调用模式检测 | 第 3 章 |

**纵深防御**——每层都假设上面的层可能失效。

## 动手环节

练习 1：搭一块黑板。声明一条 `append` 通道（`kernel/channels.py`），两个节点各写一个键，再加一个 `when` 条件边——"两个键都齐了才激活下游节点"。跑通后观察：不声明 reducer 的多写会直接报 `AmbiguousWrite`。

练习 2：找到交接的兜底。打开 `kernel/scheduler.py`，找到 `_apply_handoffs` 调用的 `_check_growth` 和 `_MAX_PLAN_NODES` 上限——确认交接链超过上限会停下来报错，而不是无限接力。
