## 2.1 问题：内核不能绑死任何一家模型

框架内核要调用大模型。模型厂商把自己的服务开放给程序员的方式，是通过 API——应用程序接口，这里指厂商在网络上提供的一组调用入口，你按约定的格式发 HTTP 请求，它返回结果。直接用厂商 API 写代码比较麻烦（要自己管鉴权、重试、各种参数编码），所以厂商通常会发布 SDK（软件开发包）：一个官方的 Python 库，把这些细节封装好，你 `pip install` 之后几行代码就能调通。比如 OpenAI 的 Python 库。

最直接的写法，就是在循环代码里直接调用某一家的 SDK。这样写当天就能跑通，但四个麻烦会陆续找上门，一个比一个深。

**第一个麻烦：换模型等于改内核。**今天用 OpenAI，明天想换 DeepSeek 或者本地部署的模型，你就得打开最核心的循环代码动手改。内核是全框架最不该频繁改动的地方，现在却成了换模型的必经之路。

**第二个麻烦更疼：测试必须连真实 API。**跑一遍测试套件要花真金白银；更糟的是模型输出有随机性，同样的输入两次可能得到不同结果，你连"断言结果正确"都做不到——测试要的是确定性，真模型给的恰恰是不确定性。

**第三个麻烦：格式散落。**每家 SDK 返回的数据结构都不一样，OpenAI 一个形状，Anthropic 另一个形状。如果内核直接消费这些原生结构，"翻译"的代码就会散布在循环的各个角落，每个用到模型输出的地方都要懂每家方言。

**第四个麻烦：各家特性打架。**流式输出的接口、缓存字段的名称、工具调用的格式，每家一套方言。每接一家新厂商，就要把所有差异点重新对一遍表，接第三家的时候你已经在对一张几十项的表了。

这四个麻烦指向同一个结论：内核和模型之间需要一层隔离。这就是第 1 章讲过的端口（port）：一份最小化的接口约定，规定了"我要什么、你给什么"，至于约定背后是谁在干活，内核不关心。实现这份约定的翻译层叫适配器（adapter），它负责把某一家 SDK 的私有格式翻译成框架的标准格式。

本章要解剖的，就是模型层的这个端口。它是全框架最小的一个端口，很适合当第一个精读对象。先看它的完整定义：

```python
@runtime_checkable
class LLMClient(Protocol):
    """Structural interface every provider adapter satisfies (duck-typed)."""

    async def complete(
        self,
        messages: MessageList,
        *,
        system: str | list[dict[str, Any]] = "",
        tools: list[dict[str, Any]] | None = None,
        config: LLMConfig | None = None,
        on_chunk: Callable[[str], Awaitable[None]] | None = None,
    ) -> LLMResponse:
        ...
```

这段代码来自 `src/prodagent/ports/llm.py`，是完整原文，没有删节。第一次看会有不少读不懂的符号：`Protocol` 是什么，`async def` 和普通 `def` 差在哪，参数列表里那个孤零零的星号是干嘛的，`Callable[[str], Awaitable[None]]` 这串又怎么读。这些正是本章三个插曲要补的内容，补完再回来逐行精读它。

## 2.2 插曲：鸭子类型与 Protocol

### Python 的老传统：只看行为，不问出身

Python 有个流传很广的说法叫**鸭子类型**：如果一个东西走起来像鸭子、叫起来像鸭子，那我们就当它是鸭子。听起来像玩笑，其实说的是一个严肃的机制：Python 判断一个对象能不能用，只看它有没有需要的方法和属性，不看它是哪个类变出来的。

最老的例子是内置函数 `len()`。你调用 `len(x)` 的时候，Python 只关心 `x` 身上有没有 `__len__` 方法。字符串有，列表有，你自己定义的类也可以有：

```python
class Playlist:
    def __init__(self, songs):
        self.songs = songs

    def __len__(self):              # 只要定义了这个方法
        return len(self.songs)

p = Playlist(["晴天", "稻香"])
print(len(p))                       # 2 —— len() 一视同仁
```

`Playlist` 没有继承任何"可测量"基类，但 `len()` 照样接受它。这就是"只看行为，不问出身"。

这个传统让写代码很自由，但在读大型代码库时会遇到一个实际的痛点：一个函数接收参数 `car`，那它到底要求 `car` 有哪些方法？这个约定没有地方写，你只能去读函数的实现，或者指望注释齐全。代码量一大，这类"隐含的约定"就成了理解成本的大头——每一个读代码的人都要自己重新发现一遍约定。

### 老办法：抽象基类，以及它的两个缺陷

传统的解决办法是用**抽象基类**，教科书里通常缩写为 ABC（Abstract Base Class）。做法是先定义一个基类，把约定写在基类里，然后要求所有实现类都继承它：

```python
class BaseLLM(ABC):
    @abstractmethod
    async def complete(self, messages): ...

class OpenAIAdapter(BaseLLM):       # 必须继承
    async def complete(self, messages): ...

class FakeLLM(BaseLLM):             # 测试假件也必须继承
    async def complete(self, messages): ...
```

"继承"是类机制里的一条父子关系：子类自动拥有父类定义的一切，并可以改写扩展。`@abstractmethod` 是一个标记，意思是"这个方法只声明了形状，实现是每个子类自己的义务"。这样约定确实写下来了，mypy 也能检查"你声明自己是 BaseLLM 的子类，但没实现 complete"。但它有两个在实际工程里很烦人的缺陷。

第一个缺陷是，**测试用的假件被迫依赖框架**。你看上面的 `FakeLLM`，它只是想在测试里冒充一个模型，却必须先 import 框架的基类来继承。从此框架每改一次基类，所有假件都要跟着改。本来测试代码应该站在框架外面敲打它，现在却被缝在了框架里面——你想拿它去测别的框架，还得先拆掉这根线。

第二个缺陷是，**第三方类无法加入**：别人已经写好的类，方法签名跟你的约定完全一致，按鸭子类型的道理它就该能用；但就因为它定义的时候不知道你的基类存在、没有继承那个基类，它就不算数。想让它算数，你得去改别人的代码（往往不可能），或者在外面再包一层（又多了一层要维护的东西）。

### Protocol：把口头默契变成书面合同

Python 3.8 之后有了更好的答案：`typing.Protocol`。它做的事情可以这样理解：鸭子类型本来是一种口头默契——"长得像就算数"，Protocol 把这份默契写成了书面合同。写法上，它看起来像一个只定义了方法签名、不写实现的类：

```python
class LLMClient(Protocol):
    async def complete(self, messages, *, ...): ...
```

规则是：任何一个类，只要有一个签名对得上的 `complete` 方法，就**自动**满足这个协议。注意"自动"两个字——不需要继承，不需要 import，协议的定义方和实现方可以完全不知道对方的存在。上一段的两个缺陷就此同时消失：假件不用再依赖框架，第三方类不用改一行代码就自动入伙。

你可能会问：这不又回到鸭子类型了吗？区别在关键的一步：因为约定现在是写成类型的，mypy 就能拿着它做静态检查。你把一个长得不像的对象传给要求 `LLMClient` 的参数，mypy 在你运行程序之前就会报错。运行时的默契没变，变的是多了一道编译前的安检——这就是 Protocol 相对裸鸭子类型的全部增量，也是它值得存在的理由。

还有一个小词顺便讲掉：端口定义上方那行 `@runtime_checkable`，是给 Protocol 加的一个开关，意思是"允许在程序运行时用 `isinstance(x, LLMClient)` 检查某个对象是否长着协议要求的那些方法"。它只查方法名是否存在，不查签名细节——精确的检查交给 mypy 做静态完成。框架在组装时用它做一次防御性的早期报警，比如把一个明显不完整的对象挡在门外并给出清晰的错误。

### 现在回来逐行读这个端口

有了上面的铺垫，我们逐行读 `LLMClient`。第一行 `async def complete` 说明这是个异步函数，异步是什么、为什么模型调用需要它，2.3 节整个插曲来讲，这里先放着。第一个参数 `messages` 是对话历史，类型 `MessageList`，它其实就是"消息字典的列表"的别名——每条消息长成 `{"role": "user", "content": "..."}` 这样。

接下来你会看到一个孤零零的星号占了一行。这是一条参数传递规则的分界线：**星号之后的参数，调用时必须写参数名，不能按位置传**。也就是说，你必须写 `complete(messages, config=cfg)`，不能写 `complete(messages, cfg)`。为什么要强制这个？因为按位置传的调用处是没人看得懂的，`complete(m, "提示词", tools)` 里第三个参数是什么全靠数；而 `complete(m, system="提示词", tools=...)` 一眼就明白。当参数超过三个，强制写名字是工业代码里常见的习惯，你在后面章节会不断见到这个写法。

`system` 参数是系统提示词，可以是纯文本，也可以是一组分段的字典，默认为空。`tools` 是本轮可用的工具定义列表，传 `None` 表示这轮没有工具可用。`config` 是本次调用的参数配置，传 `None` 表示让适配器用它自己的默认配置。这三个都不难。

真正的硬骨头是 `on_chunk` 的类型注解，我们拆开读。最外层是 `Callable[[str], Awaitable[None]]`。`Callable` 的意思是"可以被调用的东西"，也就是函数；它的方括号里有两项，第一项是参数类型列表，第二项是返回值类型。所以 `Callable[[str], X]` 读作"接收一个字符串参数、返回 X 的函数"。那 X 处的 `Awaitable[None]` 呢？`Awaitable` 表示"可以被 await 等待的东西"，`Awaitable[None]` 就是"等待完得到 None"。两段拼起来：`on_chunk` 是一个接收字符串的异步函数。再套上最后的 `| None`，完整含义是：这个参数可以不传；传的话，就传一个异步函数，框架每收到一小段模型输出就会调用它一次。它是干什么用的，2.5 节讲流式输出时你会看到。

最后返回值 `-> LLMResponse`，一个规范化的响应对象，2.5 节精读。

现在退后一步看整体。这个端口全部的内容是一个方法，没有连接、断开、鉴权、初始化——那些事情藏在适配器内部，端口只约定"一次调用"的形状。为什么刻意做得这么小？因为端口的大小直接决定实现的成本：一个方法的约定，任何人拿一百来行就能实现一个新适配器；要是约定有二十个方法，就没有人愿意实现第二次。这是你在这本书里遇到的第一条可以带走的设计准则：**接口越小，替换越容易。**

## 2.3 插曲：async 第一课

### 程序的时间花在哪：IO 与 CPU

要理解异步，先要看清楚程序的时间花在哪。程序做的无非两类事情：一类是 CPU 在计算，真正在干活——排序一个列表、解析一段 JSON；另一类是在等待外部世界回话，比如等网络请求返回、等磁盘读完数据。程序与外部世界的一切数据交换统称为 IO（Input/Output，输入输出），所以这类等待也叫 IO 等待。

模型调用是极端典型的 IO 型工作：发出一个 HTTP 请求，等上几秒钟，收到响应。在那几秒里，你的程序什么都没算，CPU 闲着，就是干等。你可以用吃饭类比：点完菜等上菜的十分钟里，你不会傻坐着只等这一道菜——你会刷手机、回消息，让多件事的"等待"重叠起来。

现在考虑同步代码怎么处理两个模型调用：发第一个请求，干等几秒，收完；然后发第二个，再干等。总耗时是两次等待相加。问题在哪？等待本身没有错，错在等待没有重叠——你等第一个的时候，明明可以同时把第二个也发出去，反正等的是两个不同的远端。

### 异步的机制：等的时候让给别人

Python 的异步编程（标准库叫 asyncio）解决的就是"让等待重叠起来"。它的基本设定是**单线程加一个事件循环**。先把两个词都讲明白。**线程**是程序里一条独立的执行流，一个程序可以有多条线程同时推进；"单线程"意味着同一时刻只有一条执行流在真正运行。**事件循环**（event loop）是这条线程里的一个调度员：它维护一张表，记着哪些任务在等什么、哪些任务已经就绪，然后不知疲倦地循环——把就绪的任务拿出来执行一段，执行到"我要等 IO"就把它挂起，换下一个就绪的任务上。所有任务就在这一条线程上轮流坐庄，谁也不真正并行计算，但大家的等待时间互相重叠了。

语法上你需要认识三样东西，一个最小的例子就能讲完：

```python
import asyncio

async def fetch(name: str, seconds: float) -> str:   # ①
    await asyncio.sleep(seconds)                     # ②
    return f"{name} 完成"

async def main() -> None:
    a = await fetch("A", 1.0)
    b = await fetch("B", 1.0)
    print(a, b)

asyncio.run(main())                                   # ③
```

第一，`async def` 定义的函数叫**协程函数**（coroutine function），调用它得到的东西叫协程——可以把协程理解为"一个可以中途暂停、之后再恢复执行的函数"，这是它和普通函数的本质区别。调用协程函数不会立刻执行，这一点很反直觉，下面单说。第二，`await` 只能出现在协程函数里，意思是"我现在要等这个东西，等待期间把执行权让给别的任务"。上面用 `asyncio.sleep` 模拟一次一秒钟的 IO 等待——真实场景里这里会是一个网络请求。第三，`asyncio.run` 负责启动事件循环并跑起最外层的协程，一个程序通常只在入口处调用一次。

刚才的 `main` 是串行的：先 `await fetch("A")`，等 A 完全结束，才开始 B，总耗时约两秒。要让两个等待重叠，用 `asyncio.gather`：

```python
async def main() -> None:
    a, b = await asyncio.gather(
        fetch("A", 1.0),
        fetch("B", 1.0),
    )
    print(a, b)
```

`gather` 把传入的多个协程同时放进事件循环，等它们全部完成后，**按传入的顺序**把结果排好交给你（注意，结果顺序和谁先完成无关，这一点在第 5 章并行执行工具时还会用到）。这个版本总耗时约一秒。省下的那一秒，就是原本白白流走的等待时间。

### 新手第一坑：调用不执行

现在说那个反直觉的点。如果你写 `fetch("A", 1.0)` 而不加 `await`，会发现什么都没发生：没有等待，没有返回结果。原因是协程函数被调用时返回的是一个"待执行的协程对象"，相当于一张尚未兑付的票据；要让它真正跑起来，必须 `await` 它，或者把它交给 `gather` 这类调度器。这个坑几乎人人踩过，症状是"函数好像没执行"，排查时第一怀疑对象永远是漏了 `await`。好消息是 mypy strict 能查出大部分这类错误。

### 回到端口

补完这块基础，端口签名里的 `async def complete(...) -> LLMResponse` 可以完整读懂了：一次异步的模型调用。调用它的循环内核会 `await` 这个调用，在等待模型响应的那几秒里，事件循环会去推进别的协程，比如并行执行中的工具调用。整个框架从里到外都是异步的，因为 Agent 的工作负载几乎全是网络 IO——等模型响应、等工具里的 HTTP 请求、等存储读写。这是你第一次系统学 async，也是唯一一次从零讲，后面章节直接使用这些概念。

## 2.4 插曲：dataclass 入门

### 先手写一遍，感受痛点在哪

模型调用的配置需要一个对象来装：模型名、温度、最大输出长度这些。按最基础的 Python 写法，你会写一个这样的类：

```python
class LLMConfig:
    def __init__(self, model="", temperature=0.0, max_tokens=8192):
        self.model = model
        self.temperature = temperature
        self.max_tokens = max_tokens

    def __repr__(self):
        return (f"LLMConfig(model={self.model!r}, temperature={self.temperature!r}, "
                f"max_tokens={self.max_tokens!r})")

    def __eq__(self, other):
        if not isinstance(other, LLMConfig):
            return NotImplemented
        return (self.model == other.model
                and self.temperature == other.temperature
                and self.max_tokens == other.max_tokens)
```

三个方法各自干嘛，先补齐常识。`__init__` 在创建对象时被调用，你在 `__init__` 里把传进来的参数存到对象身上（`self.model = model` 就是"把这个对象的 model 属性设成传进来的值"），之后 `cfg.model` 才能取到值。`__repr__` 决定 `print(cfg)` 时显示什么，不写的话打印出来是一串内存地址，调试时等于瞎的。`__eq__` 决定 `cfg1 == cfg2` 按什么比，不写的话 Python 比的是"是不是同一个对象"，两个内容完全相同的配置会被判为不相等——而配置对象恰恰经常需要按内容比较。

现在盯着这段代码看一个问题：这个类真正想表达的信息是什么？其实就是"配置里有三个字段：model、temperature、max_tokens"。这条信息你写了几遍？`__init__` 的参数列表一遍，`__init__` 的赋值一遍，`__repr__` 一遍，`__eq__` 又一遍——整整四遍。这种"每个类都要重复编写、内容几乎可以预料、不承载新信息"的代码，有个专门的名字，叫**样板代码**（boilerplate）。样板代码的危害不在于占篇幅，而在于它要靠人来保持同步：以后加第四个字段，四处都要改，漏掉任何一处就是 bug，而且是隐蔽的那种。比如忘了在 `__eq__` 里比较新字段，两个配置看起来相等、实际不等，测试就会时好时坏，非常难查。

### @dataclass：字段只写一遍

Python 3.7 起，标准库提供了 `dataclasses` 模块来消灭这类样板。用法是在类上方加一行 `@dataclass`：

```python
from dataclasses import dataclass

@dataclass
class LLMConfig:
    model: str = ""
    temperature: float = 0.0
    max_tokens: int = 8192
```

`@dataclass` 这种写法叫**装饰器**。装饰器的完整机制第 5 章会从零讲，先记住它的用法和含义：写在类定义的正上方，表示"请按某种方式加工下面这个类"。`@dataclass` 加工的方式是：读一遍类体里那些带类型注解的赋值语句，然后替你生成 `__init__`、`__repr__`、`__eq__` 三个方法。

类体里那些赋值语句有个名字，叫**字段声明**，"声明字段"说的就是写这些行。`model: str = ""` 读作：model 是一个字符串字段，默认值是空字符串。你把字段声明一遍，dataclass 替你生成四份样板。刚才的同步问题就此消失，因为字段的信息现在只有一个来源，其余全部从它派生。六个字段以内的类，dataclass 版本几乎总是十行以内，而且加字段就是加一行声明。你在第 1 章看过的 `AgentConfig`、后面各章的 `Budget`、`LLMResponse`，全是 dataclass——这个仓库里凡是"装数据"的类基本都交给它。

### 一个必须搞懂再走的坑：可变默认值

`model: str = ""` 直接写默认值没有问题，因为字符串创建之后不能被修改，这类对象叫不可变对象。但如果字段的默认值是列表或字典，直接写就会出错：

```python
@dataclass
class Bad:
    steps: list = []          # 错误写法
```

这段代码能运行，不报任何错，但行为是错的。原因要掰开讲。Python 计算"字段的默认值"的时机，不是每次创建新对象的时候，而是**类定义被加载的那一刻**——那次求值得到一个具体的列表对象，然后所有用默认值的实例共享它。于是 `a = Bad()` 和 `b = Bad()` 里的 `a.steps` 和 `b.steps` 是同一个列表，你往 `a.steps` 里加一项，`b.steps` 也会多出一项。这个坑不是 dataclass 特有的，普通函数的默认参数同样如此，是 Python 语言层面的行为。

正确写法是把"默认值"换成"默认值工厂"——工厂就是"被调用时生产一个新东西"的函数——也就是告诉 dataclass：每次创建新实例时，现场调用一次这个函数来生产默认值：

```python
from dataclasses import dataclass, field

@dataclass
class Good:
    steps: list = field(default_factory=list)
```

`field(default_factory=list)` 里的 `list` 就是工厂——`list` 本身是个函数，调用它返回一个全新的空列表。这样一来每个实例的 `steps` 各是各的。记住一条没有例外的规则：凡可变默认值（列表、字典、集合），必须走 `default_factory`。你会在框架源码里到处看到这行惯用法，现在你知道它防的是什么了。

### 造完对象再自动加工一步：`__post_init__`

dataclass 还提供一个进阶口子：`__post_init__`。它是一个方法名，固定在对象创建完成之后自动被调用，适合放"根据已有字段推导更多信息"的逻辑。框架的 `LLMConfig` 用它做了一件很实用的事：

```python
@dataclass
class LLMConfig:
    model: str = ""
    temperature: float = 0.0
    max_tokens: int = 8_192
    timeout_seconds: float = 60.0
    cost_per_million_input: float = 0.0     # 单价：每百万输入 token 多少美元
    cost_per_million_output: float = 0.0
    ...

    def __post_init__(self) -> None:
        if not self.model:
            from prodagent.llm.providers import detect_default_model
            self.model = detect_default_model()
        if self.cost_per_million_input == 0.0 and self.cost_per_million_output == 0.0:
            from prodagent.llm.pricing import pricing_for_model
            table = pricing_for_model(self.model)
            if table is not None:
                self.cost_per_million_input = table.input_rate_per_million
                self.cost_per_million_output = table.output_rate_per_million
```

代码来自 `src/prodagent/ports/llm.py`，略有删节。逻辑是两段自动填充：你没写模型名，它按环境变量检测一个默认模型；你没填单价，它去内置定价表里查这家模型的单价填进来。效果是用户什么都不配，预算的花费轴默认就是活的。如果用户显式填了价格，显式的永远优先；查不到的模型（包括假模型）定价记为零，花费轴自动失效，其余三个预算上限照常工作。

这里有一条设计思路可以记下：**能从已有信息推导出来的配置，就不要让用户填。**让用户手填单价，填错一位小数，预算的花费轴就悄悄失灵，这种错很难被发现；自动填充加显式覆盖，把出错面缩到最小。

## 2.5 精读：一次模型调用的完整契约

三个插曲补完，主线继续。一次模型调用的契约分"进"和"出"两侧，一节一节看。

### 进的一侧：消息列表

`messages` 是对话历史，每条消息长什么样？框架选的是业界通用的线格式——"线格式"（wire format）指数据在网络上传输时的实际形态，因为对话列表每次请求都要原样发给模型厂商，故有此名。三种角色三种形态：

```python
# 用户消息
{"role": "user", "content": "巴黎今天天气如何？"}

# assistant 消息可能带工具调用
{"role": "assistant", "content": "", "tool_calls": [
    {"id": "call_abc", "type": "tool_use", "name": "search",
     "input": {"query": "巴黎天气"}}]}

# 工具消息必须带 tool_call_id，与请求配对
{"role": "tool", "tool_call_id": "call_abc", "content": "搜索结果..."}
```

角色一共三种：`user` 是用户说的话，`assistant` 是模型说的话，`tool` 是工具执行的结果。注意一个精巧的配对关系：assistant 消息里说"我要调用 id 为 `call_abc` 的 search"，工具消息必须带着同一个 `call_abc` 回来——这个 id 就是把"申请"和"回执"钉在一起的那颗钉子。模型下一轮看到对话时，靠它知道哪条结果对应哪次申请。

注意 Message 就是普通的字典，没有封装成类。为什么？三个理由：与各家模型 API 的线格式直接对齐，转换层最少；序列化反序列化零成本（存盘就是存 JSON）；上下文压缩时操作字典比操作对象灵活。这也是一条刻意的取舍：**消息格式以业界事实通用语为规范，不自创中立格式**——自创一套"框架语"要多一层翻译，全行业还得重学。代价是某些厂商特有的东西（比如思维块——部分模型在正式回答前会先输出一段推理过程文本，业界称为 thinking，即思维块）在通用格式里没有座位，对策是扩展键原样携带、不翻译。

### 出的一侧：LLMResponse

所有模型的方言都被翻译成同一种普通话，就是返回值 `LLMResponse`：

```python
@dataclass
class LLMResponse:
    """Normalised response from any LLM adapter."""
    content: str                                  # 文本输出
    tool_calls: list[ToolCall] = field(default_factory=list)
    stop_reason: StopReason = StopReason.END_TURN
    input_tokens: int = 0
    output_tokens: int = 0
    model: str = ""
    cache_read_tokens: int = 0
    cache_write_tokens: int = 0
    ...
```

代码来自 `src/prodagent/kernel/types.py`，有删节。字段不少，但真正要盯住的是三组。

第一组是 `tool_calls`，模型请求调用的工具列表。这个字段是整个 Agent 体系的命脉所在：模型自己不执行任何动作，它只是在回复里说"我想调用 search 工具，参数是这些"，真正的执行是下一章循环内核的事。**模型负责想，框架负责做**，两者的分界线就是这个字段。

第二组是 `stop_reason`，模型这次为什么停下来。它是一个枚举——枚举（enum）是一种"值只能从列出的几个里选"的类型，写它就是为了把可选答案钉死在一个封闭集合里。这个枚举一共四个值：

| 值 | 含义 | 循环的反应 |
|---|---|---|
| `END_TURN` | 自然说完 | 结束本轮 |
| `TOOL_USE` | 想调工具 | 执行工具，把结果接回对话 |
| `MAX_TOKENS` | 输出被长度截断 | 处理截断 |
| `CONTENT_FILTER` | 被安全策略拦下 | 处理拦截 |

你可能觉得这个字段可有可无——模型说完话不就完了吗？不是的。循环内核拿到响应后要做的第一个判断就是"接下来干什么"，而判断的依据必须是一个可靠的、封闭集合里的值。这和第 3 章讲 `StepStatus`（步骤状态机）时用的是同一招：**把决策依据类型化**。循环读到 `TOOL_USE` 就知道该去执行工具，不需要解析模型的自然语言去猜它的意图——猜自然语言是没有可靠性可言的，而枚举值要么对得上要么对不上，没有中间态。

第三组是 token 计量：`input_tokens`、`output_tokens`、`cache_read_tokens`、`cache_write_tokens` 四个字段，它们是预算的燃料表，下面马上讲到一个跟它们有关的真实陷阱。

### 口径坑：数字不能直接信

token 计量有个不为人熟知的坑：各家模型 API 返回的 `input_tokens`，统计口径不一致——这里的"口径"指"算不算某些类 token"的算法约定。有的厂商把缓存 token 算在输入 token 里，有的不算。如果适配器把各家数字原样抄进来，同样的真实消耗在不同模型下会算出不同的成本，预算的花费轴就系统性失准了。

所以框架定了一条规范：`input_tokens` 一律折算成"全包含"口径，也就是普通输入加缓存读加缓存写，适配器负责把各家原生数字折算到这个口径。花钱的时候再从全包含的基数里把缓存部分减出去，按各自的价格线分别计算。这段逻辑是端口上的一个纯函数——纯函数指输出只由输入决定、执行过程不读写任何外部状态的函数，这种函数最好测也最可靠——整段读一遍：

```python
def token_cost_usd(response: LLMResponse, pricing: PricingTable) -> float:
    cache_read = response.cache_read_tokens or 0
    cache_write = response.cache_write_tokens or 0
    # Providers count cache tokens inside input_tokens; they carry their own
    # (discounted / premium) price lines, so the plain-input base excludes them.
    input_billed = max(0, response.input_tokens - cache_read - cache_write)
    cost = (
        input_billed / 1_000_000 * pricing.input_rate_per_million
        + response.output_tokens / 1_000_000 * pricing.output_rate_per_million
        + cache_read / 1_000_000 * (pricing.input_rate_per_million * pricing.cache_read_discount)
        + cache_write / 1_000_000 * (pricing.input_rate_per_million * pricing.cache_write_premium)
    )
    return max(0.0, cost)
```

代码来自 `src/prodagent/ports/llm.py`，是原文。算法就是四类 token 各乘各的单价再相加：普通输入全价，输出全价（通常比输入贵），缓存读打折扣（大约零点一倍），缓存写有溢价（一点二五倍）。代码注释里专门强调"four token classes, four price lines — never a blended average"：**四类 token 四条价格线，绝不算混合均价**。混合均价看起来省事，实际上必然对某些用量结构多算、对另一些少算，预算就不准了。算钱这件事，分项记账是唯一可靠的做法。

这条规范还影响预算的 token 轴：计费 token 等于总 token 减去缓存读，因为缓存读几乎不花钱，不应该占用 token 预算的额度。第 4 章讲预算时会用到这个推论，到时候你会再遇到它。

### 流式回调 on_chunk

最后讲讲参数里那个"接收字符串的异步函数"。模型生成文本不是一整块蹦出来的，而是一小段一小段陆续出来的——生成一个词、传一个词。`on_chunk` 的用途是：适配器每收到一小段，就实时调用它一次。前端打字机效果、思维链实时展示，都靠它。

你可能会问：为什么不把所有小段收集成一个列表放进返回值？因为返回值 `LLMResponse` 的角色是完整响应，循环内核需要的是完整的结果——工具调用列表、token 统计都在里面；流式片段只是旁路的直播，两者服务的对象不同。回调方案让它们各走各的通道：完整结果走返回值，片段走回调。不支持流式的适配器可以完全忽略 `on_chunk`，接口照样成立。

流式的世界底下还埋着一条看不见的守卫，顺路看一眼。模型调用偶尔会在传输中途断掉，适配器之下有一层传输重试，负责可重试的失败：限流（厂商对单位时间调用次数的上限，超了会被拒绝）和网络闪断这类，按指数退避重试——退避指每次重试前先等一会儿，指数退避是让这个等待时间逐次翻倍，给对端喘息的时间，第 5 章会细讲。但有一种失败绝不能透明重试：**第一个流式片段已经交给消费者之后的中途失败**。重试会把已经交付的前半段再放一遍，用户看到一条消息变成两条。所以这层守卫（代码里叫 DeliveryGuard，住在 `llm/http_retry.py`）在首笔交付时做标记，之后一旦失败就不再重试、直接上抛。道理和第 5 章要讲的"错误分类驱动重试"同源：什么都没发生的失败可以重来，发生了一半的失败必须显式处理——这条分界线在分布式系统里有个名字叫幂等边界（同一操作执行一次和执行多次效果相同的保证），你在第 7、9、10 章会一次次遇到它。

## 2.6 FakeLLM：把确定性做进测试

端口思维最直接的受益者是测试。`src/prodagent/llm/fake.py` 里有一个假模型 `FakeLLMAdapter`，它按你写的剧本演戏。配套的 `script()` 函数让剧本写起来很省事：

```python
from prodagent.kernel.types import LLMResponse, StopReason, ToolCall
from prodagent.llm.fake import FakeLLMAdapter, script

fake_llm = script(
    {"tool": "search", "params": {"query": "巴黎天气"}},
    {"content": "巴黎今天晴，25°C。"},
)
```

每一行字典是一轮的台词：第一轮模型说"我要调用 search 工具"，第二轮给出最终回答。每次 `complete()` 调用按顺序取走一条，用完为止——排队规则就是先进先出，先写的先被消费。

一个假模型，凭什么专门用一节讲？算一笔账就清楚了。框架有一千三百多个测试，如果都用真实模型：同样的输入可能得到不同输出，你没法写断言；厂商接口有限流，测试套件会随机失败；跑一遍套件可能花掉几十美元；每个测试还要等上几秒到几十秒。换成剧本化的假模型，这四笔账全部清零：同一个剧本必然演出同一场戏——这就是**确定性**（determinism），同样的输入必然得到同样的输出；不联网不花钱；毫秒级演完。可以说，没有 FakeLLM，这个框架的测试体系根本建不起来。后面每一章你都会在动手环节里用到它。

还有一点呼应 2.2 节：`FakeLLMAdapter` 没有继承任何基类，它只是恰好长着协议要求的那个 `complete` 方法，mypy 就认定它是一个合法的 `LLMClient`。测试世界和框架世界之间零 import 耦合，这是端口合同直接兑现的红利。多 Agent 测试（第 10 章）还有按 Agent 名字分派不同剧本的 `RoutingFakeLLM`，思路相同，到时候再见。也请你先记住这个假模型——第 12 章你会发现，它正是"可回放运行时"的原型：手写剧本和生产录像带，是同一个机制的两个用途。

## 2.7 换模型不改代码：让配置承载变化

端口解决了结构问题，还剩一个选择问题：一次运行到底用哪家模型？框架的答案是不在代码里写死，全部交给配置。具体说是一组**环境变量**——操作系统提供的一层全局配置：程序外部设好值，程序启动时读进来，改配置不用改代码。检测的优先级是确定的：环境变量 `USE_FAKE_LLM=1` 用假模型；设了 `LLM_BASE_URL`、`LLM_API_KEY`、`LLM_MODEL` 就用任意 OpenAI 兼容端点；设了 `ANTHROPIC_API_KEY` 用 Anthropic 原生；什么都没设，用假模型兜底。检测逻辑在 `src/prodagent/llm/providers.py`。

这里有一个刻意的设计：框架不内置任何厂商清单。它不关心你的 `LLM_BASE_URL` 指向 DeepSeek、Qwen、Moonshot 还是你自建的服务——市场上每出现一家新厂商，框架一行代码都不用改，你改一个环境变量就接上了。这条原则和端口是一体两面：**变化最频繁的东西，用配置和数据去承载，不要用代码分支承载。**如果你在代码里写 `if vendor == "openai"`，每出一家新厂商就要改一次代码发一个版；配置驱动则把这些成本归零。以后你自己设计系统的时候，可以先问一句：这里的"变化轴"是什么？把轴让给配置，是多数时候的正确答案。

## 2.8 让模型稳定吐 JSON：三层防线

模型层还有一块常被低估的硬骨头：让模型输出结构化数据。很多场景需要模型返回一个严格的 JSON 对象——工具的参数、结构化的分析结果都是。但模型的本性是"接着上文往下续写"：你让它"只返回一个 JSON"，它常常先客气一句"好的，结果如下："再附一段代码块，甚至好心地在 JSON 外面裹一层解释文字。这不是模型坏了，是续写天性使然。可你的程序要拿这段文字去解析，开头不是 `{` 就当场报错。

框架的解法是三层防线，一层比一层深。

第一道是**提取**：从模型文本里把真正的 JSON 找出来。分两步：先剥掉 markdown 代码围栏——markdown 里用三个反引号包住代码的写法，模型很爱用它；然后从第一个花括号开始逐字符扫描，用一个深度计数器找到第一段括号配平的片段：遇到 `{` 加一，遇到 `}` 减一，减到零就收工。为什么不直接对花括号做正则匹配？正则表达式是一种文本模式匹配语言，但它处理不了任意深度的嵌套——`{"a": {"b": 1}}` 里的两层括号，正则分不清哪个 `}` 配哪个 `{`。扫描还有个细节要处理：字符串内部出现的括号不能计数，`{"text": "一个 } 符号"}` 里的 `}` 属于字符串内容，数了它配平就提前收工、JSON 就截断了。

第二道是**校验**：`json.loads` 把文本解析成 Python 字典，再用 pydantic（一个"用类型注解做运行时校验"的库：你声明"name 必须是字符串、age 必须是整数"，它逐字段核对，不符就报出具体哪里错了）把字典验证成字段类型都可靠的对象。哪一步失败，都统一包装成一种结构化错误，不把几种不同的异常漏给上层——上层不需要知道失败发生在哪一层，只需要知道"这次输出不合格，原因是什么"。

第三道最体现设计思想：校验失败时**不放弃也不抛给用户**，而是把上一轮的回答和错误原因一起追加回对话，补一句"你上次的输出没通过校验，这是原因，请只返回符合要求的 JSON"，然后重试。模型读到自己上次错在哪，下一次往往就改对了。你在第 5 章会看到工具错误也是这样处理的——模型会犯错是常态，框架要做的是给它看着错误改正的机会，而不是一错就中断整个运行。
