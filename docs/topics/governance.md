# 策略与治理

十个团队共用一个平台，A 团队的 Agent 能不能看到 B 团队的数据？同一个角色下，A 只能查客户列表、B 才能发起审批流，怎么做操作级授权？每次工具调用怎么留下不可篡改的记录？

这些问题共享同一个架构前提：**框架不认识你的组织，但它必须给你足够的卡位**。这一章讲这些卡位在哪、怎么用，以及一个平台级治理体系在这套机制上怎么长出来。

## 卡位一：Gate——策略的注入口

`kernel/bus.py` 的 Gate 枚举定义了九个阻塞式检查点，覆盖 Agent 生命周期里所有“能不能继续”的决策位：会话开始、工具调用、工具结果、文档写入、Agent 交接、运行完成……每个位上可以挂任意多个检查器，**首个 veto 即停**：

```python
registry.register_checker(Gate.TOOL_CALL, my_policy)   # 你的规则
registry.register_checker(Gate.TOOL_CALL, org_rbac)    # 组织的规则
```

关键在于语义边界：框架提供的是**在正确的时机、以正确的阻塞语义调用你的策略**，策略本身（什么是越权、谁能批多少额度）一无所知。RBAC 是往 `TOOL_CALL` 和 `DOCUMENT_ADD` 挂角色检查；操作级授权是挂细粒度动作白名单；数据租户隔离是往 `SESSION_START` 挂 team 归属校验——同一套卡位，三种治理体系。

这也回答了“为什么框架不内置权限引擎”：内置的 RBAC 对每个组织都是错的起点，而卡位是所有权限体系的公因子。

## 卡位二：消息平面的 GATE 位与审计

跨 Agent 的每次穿越（[协作](../tour/07-multiagent.md)那站的 Crossing 管道）自带一个安全位：`GateInterceptor`（`coordination/messaging/interceptors.py:150`）在消息投递前查询挂着的检查器，veto 则整条消息 strict 拒绝、进死信。审计位（AUDIT）在管道末端把**实际发生的穿越**记成事件——不是“应该发生什么”，是“发生了什么”。

治理的三个时序需求——事前拦截（Gate）、事中记录（audit span）、事后回放（事件流 + checkpoint）——分别落在管道的前端、末端和存储里，不用你自己拼。

## 卡位三：隔离边界

playground 演示了最小形态的租户隔离：`playground/registry.py:132` 给每个示例的存储注入独立 namespace（`-playground-{name}` 后缀），示例之间共享进程、互不见数据。放大到组织级就是：namespace → schema → 库，隔离粒度由 `backends/factory.py` 的解析表决定，Agent 代码一行不改。

## 从卡位到平台

把卡位连起来，一个 Agent 平台的治理清单大致是：身份（Agent 是谁、代表哪个团队）→ 授权（Gate 检查器里的 RBAC/操作级策略）→ 边界（namespace/后端隔离）→ 证据（span + 审计 + checkpoint 的不可篡改流水）→ 回放（trace_id 串起整条链路）。每一环的机制你都在这一章和[可观测](observability.md)里见过了；把它们按组织的需求装配成体系，是平台工程的事——装配的完整推演（多租户的隔离粒度怎么选、操作级授权的策略引擎怎么设计不拖慢热路径），在专栏的企业级治理部分逐讲展开。

## 取舍

**不内置权限引擎。** 组织结构、合规要求、威胁模型千差万别，任何内置方案都是下一个组织的包袱；卡位 + 注入让治理体系成为应用的资产而不是框架的债。**审计不采样错误。** 治理场景里，事故记录的完整性高于一切——采样率可以调，错误 span 永远全量。
