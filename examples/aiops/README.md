# 故障应急

---

> 示例 #7 ——「Agent 之间的信息传递」一章的配套示例。线上告警了，主 Agent 不自己埋头查，
> 而是同时派几个子 Agent 分头诊断，查清根因后再交给平级的修复 Agent 接力。

半夜收到告警——"支付服务有问题"。一个人去查，得翻日志、看最近发了什么版、盯指标，一件
件串下来半小时就过去了。

这个例子把 **Agent 之间的协作**放在 C 位。主 Agent 自己几乎不动手查，它干的是两件事——
指挥和交班：

- **派子 Agent 分头查**：它不一件件串着来，而是一口气同时派出三个子 Agent——一个翻日志、
  一个查最近发了什么版、一个算指标——让它们并行跑，各查各的，查完各带一份结论回来。主 Agent
  还留在台上，把三份结论拼成一份故障报告。
- **交给平级 Agent 接力**：根因查清楚了，主 Agent 就把这份报告交给一个专门负责修复的平级
  Agent，自己退场。修复 Agent 接过报告接着干——开故障单、回滚、验证、写总结。

这正好呼应文章里那个核心道理：Agent 之间别"脑波直连"，别把自己一长串对话和试错全灌给对方。
派子 Agent 时，给的是一句清楚的任务（去查什么）；交给修复 Agent 时，给的是一份清楚的报告
（查到了什么、该怎么办）。对方拿到的都是干净的信息，不是主 Agent 翻日志、调工具的全部中间
过程。根因没查清的时候，主 Agent 也不瞎交，直接把人叫起来。

它还带着两样本事：一是记着历史的约束和经验（比如"这个服务回滚要走灰度"），二是修完
会把这次事故的处置套路沉淀成手册，下次类似故障直接照着走。全程每一步都有痕迹，中途
崩了能从断点恢复，不从头来。

## 本示例展示什么

- **两种协作方式**：主 Agent 派子 Agent 并行查，再交给平级修复 Agent 接力，不是一个人干到底。
- **交出去的是结论，不是一长串对话**：Agent 之间不"脑波直连"，给的是干净的任务和报告，不把对话和试错全灌过去。
- **回滚要人批准**：影响线上的动作，动手前等你点头。
- **记着经验、越用越熟**：带着历史约束，修完还沉淀手册给下次用。
- **全程可观测、崩了能续**：每步有痕迹，中途挂了从断点接着跑。

## 一次故障的处置流程

```
告警进来
  → 主 Agent 接手
      → 同时派三个子 Agent：查日志 ‖ 查部署 ‖ 算指标
      → 把三份结论拼成故障报告，判断根因
      → 根因清楚？ —否→ 把人叫起来
                   —是→ 交给修复 Agent 接力
                          → 开单 → 回滚（弹审批框）→ 验证 → 写总结
```

这是全栈示例，能力最全：多 Agent 协作、记忆、学习、可观测、审批、崩溃恢复都在里头。代码在
`agent.py`（组装）和 `child_agents.py`（子 Agent 和平级 Agent），想接生产后端（Postgres /
Neo4j / Redis）或跑评测见仓库根的 Makefile。
