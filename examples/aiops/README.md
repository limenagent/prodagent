# 故障应急

---

> 示例 #7 —— 线上告警了，Agent 并行查日志、查部署、查指标定位根因，动手回滚前停下来等你确认。

半夜收到告警——"支付服务有问题"。一个人去查，得翻日志、看最近发了什么版、盯指标，一件
件串下来半小时就过去了。

这个例子让 Agent 并行干：同时派三个子 Agent 分头去查日志签名、查最近部署、算指标异常，
各自带回一份结论。主 Agent 把三份合成一份故障报告，判断根因到底清不清楚。

根因清楚，它就把报告交给修复 Agent 接着干——去开故障单、回滚、验证指标恢复、写事后
总结。但真到了回滚那一下，它停下来等你确认：回滚是直接影响线上的动作，得人拍板。

它还带着两样本事：一是记着历史的约束和经验（比如"这个服务回滚要走灰度"），二是修完
会把这次事故的处置套路沉淀成手册，下次类似故障直接照着走。全程每一步都有痕迹，中途
崩了能从断点恢复，不从头来。

## 本示例展示什么

- **并行诊断**：同时查日志 / 部署 / 指标，不是一件件串着看。
- **找到根因能交接**：诊断完把报告交给修复 Agent 接力，不是一个人干到底。
- **回滚要人批准**：影响线上的动作，动手前等你点头。
- **记着经验、越用越熟**：带着历史约束，修完还沉淀手册给下次用。
- **全程可观测、崩了能续**：每步有痕迹，中途挂了从断点接着跑。

## 一次故障的处置流程

```
告警进来
  → 并行：查日志 ‖ 查部署 ‖ 算指标
  → 合成一份故障报告，判断根因
  → 根因清楚？ —否→ 升级 oncall
               —是→ 交给修复 Agent
                       → 开单 → 回滚（弹审批框）→ 验证 → 写总结
```

这是全栈示例，能力最全：多 Agent、记忆、学习、可观测、审批、崩溃恢复都在里头。代码在
`agent.py`，想接生产后端（Postgres / Neo4j / Redis）或跑评测见仓库根的 Makefile。
