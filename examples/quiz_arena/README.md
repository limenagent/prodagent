# 抢答竞赛场

---

> 示例 #9 —— 一场抢答赛：后台审题谁有空谁领活，台上多人抢答但只有先抢到的真算分。

这个例子用一场抢答比赛，演示两种协作方式。

后台审题，是"抢活干"：一批候选题需要人审，两个审核员谁有空谁去领下一道——不是主持人
挨个派发。有人领了活却失联了？到期自动收回、重新发。题目本身就是坏的（缺题干、缺答案）？
重试够了就扔进死信，永远不流进正式比赛。最后只有审过的题，才拿去当抢答题。

台上抢答，是"抢锁"：三个人都能答，但只有最先抢到锁的那个真正动脑算，另外两个连算都
不算——不是"三个人都算一遍、谁先算完谁赢、输了再取消"。所以每道题只有一个人真正答过。

这件事重要到要专门验：脚本跑完会硬断言——全场选手真正算分的次数加起来，必须正好等于
出了几道题。多了或少了，都说明"只有一个人真算"这个语义坏了。而且谁先抢到是真实的调度
结果，每次跑谁答哪道可能不一样，这才是抢答该有的样子。

## 本示例展示什么

- **后台审题（抢活干）**：谁有空谁领活；领了不干到期自动收回；坏题重试够了进死信，不污染
  正赛。
- **台上抢答（抢锁）**：多人能答，但只有先抢到的真算，其他人不算——不是都算了比谁快。
- **用真实计算次数硬断言**：全场真正算的次数必须正好等于题数，多了少了都算语义坏了。
- **结果不写死**：谁抢到由真实调度决定，每次跑可能不一样。

两段拼起来是一条完整流水线：审题的产出（通过的题）直接就是抢答的输入。代码在 `quiz_arena/`。
